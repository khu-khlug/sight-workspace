# 파일 업로드·삭제 기능

R2에 파일을 올리고, 제출 시 검증하고, 지우고, 주기적으로 청소하는 공통 흐름입니다.

## 개요

- **저장소**: Cloudflare R2 (S3 호환 API), 메타데이터는 MySQL의 업로드 기록 테이블
- **ID 생성**: 신규 업로드 기록 아이디와 파일 키는 ULID 기반 문자열. 레거시 파일은 기존 테이블과 객체 키를 그대로 사용
- **기준**: DB가 파일 상태를 결정한다. R2는 DB가 가리키는 객체를 보관만 한다.
- **정리 원칙**: 필요 없어진 파일과 업로드 기록은 그때그때 정리하는 것이 원칙이다. 주기적 청소는 그때그때 정리에서 빠진 것을 처리하는 안전망이며, 기본 정리 수단으로 쓰지 않는다.

## 파일 위치

```
src/main/kotlin/com/sight/domain/file/
└── FileUpload.kt            # Entity

src/main/kotlin/com/sight/repository/
└── FileUploadRepository.kt  # Repository

src/main/kotlin/com/sight/service/
├── FileUploadService.kt     # 링크 발급, 검증, 사용 처리, 삭제
└── StorageService.kt        # R2 연동 (업로드 URL 생성, 객체 존재 확인)
```

## 업로드 기록이 담는 정보

- 업로드 기록 아이디 (API의 `fileUploadId`)
- 파일 키 (R2 object key)
- 발급자 (링크를 발급받은 회원)
- 발급 경로 (링크를 발급한 API 경로. 실제 아이디가 들어간 경로)
- 업로드 완료 표시 (`is_uploaded`). 기록 첨부의 사용 여부는 연결 행으로 판단한다.
- 생성 시각
- 삭제 표시 시각 (`deleted_at`)
- 읽기 URL 캐시와 만료 시각 (`read_url`, `read_url_expires_at`)

## 디자인 패턴

- **용도별 발급 API**: 공용 Presigned URL API를 두지 않고 용도마다 발급 API를 둔다. 발급 경로로 "이 용도·이 리소스를 위해 발급된 파일인지"를 검증하고, 용도별 권한(예: 활동보고는 그룹장만)을 따로 적용하기 위해서다.
- **업로드 기록과 객체의 1:1 대응**: 링크 발급 시 업로드 기록을 먼저 만들고 그 파일 키로만 업로드하게 한다. 업로드 기록 없이 R2에만 존재하는 객체가 정상 흐름에서 생기지 않는다.
- **저장 요청 안에서 발급하는 첨부 파일**: 편집을 거쳐 저장하는 데이터(예: 기록)의 첨부 파일은 별도 링크 발급 API 없이 저장·임시저장 요청에 파일 식별자 배열을 함께 받고, 새 파일의 업로드 링크를 응답으로 돌려준다. 서버에 저장된 데이터와 파일 목록이 클라이언트의 업로드 성공 여부와 관계없이 어긋나지 않게 하기 위해서다.
- **데이터 내 파일 식별자**: 본문은 데이터 안에서만 유일한 식별자·백엔드 파일 아이디·영구 파일 주소를 가진다. 서버는 본문을 파싱하지 않고 요청의 식별자 배열만 비교하며, 조회 응답의 파일 목록은 첨부 목록·업로드 상태에 사용한다. 파일 배열은 사용자에게 첨부 목록을 제공하고 파일 연결을 관리하는 데 사용하며 본문 렌더링의 주소 매핑에는 사용하지 않는다.
- **연결 행으로 공유와 삭제 판단**: 여러 데이터가 한 파일을 참조할 수 있도록 "소유자 + 식별자 → 업로드 기록" 연결을 행으로 둔다. 연결 행이 하나도 남지 않을 때 파일을 삭제한다. 숫자 카운터는 실패·중복 요청에서 어긋나기 쉬워 쓰지 않는다.
- **본문과 파일 목록의 불일치 허용**: 서버는 본문을 읽지 않으므로 본문에 드러나지 않는 첨부 파일이 있을 수 있다. 서버의 연결 목록을 첨부 파일의 기준으로 보고, 클라이언트가 첨부 파일 목록을 따로 보여 주어 확인할 수 있게 한다.
- **비공개 버킷과 읽기 링크**: 버킷은 비공개로 두고 영구 파일 주소 접근 시 권한 검사 후 Presigned GET URL로 리다이렉션한다. 본문에는 영구 주소를 저장한다. 서명 URL은 파일별로 캐싱해 재사용한다.
- **삭제 표시 후 삭제(tombstone)**: 지울 파일은 업로드 기록에 삭제 표시를 먼저 남기고, 커밋 후 R2를 지우고, 성공하면 업로드 기록을 지운다. 실패해도 삭제 대상이 DB에 남아 있어 재시도 대상을 버킷 전체 대조 없이 찾을 수 있다.

## 흐름

### 업로드 (단일 파일 제출형)

1. 용도별 발급 API가 업로드 기록을 만들고 Presigned PUT URL을 반환한다. 이때 링크 만료 시각에 여유 시간을 더한 시각으로 업로드 확인 예약을 등록한다.
2. 클라이언트가 URL로 R2에 직접 업로드한다.
3. 클라이언트가 `fileUploadId`를 제출 API에 보낸다.
4. 제출 API가 검증을 통과시키고, 데이터 저장과 사용 처리를 한 트랜잭션에서 처리한다.

### 업로드 (저장 요청 안에서 발급하는 첨부 파일)

1. 클라이언트는 편집 중 파일을 로컬에 두고, 본문과 파일 식별자 배열(새 파일은 백엔드 아이디 없이)을 저장·임시저장 요청에 보낸다.
2. 서버는 배열을 저장된 연결 목록과 비교해 새 파일은 업로드 기록·업로드 링크·확인 예약을 만들고, 빠진 연결은 해제하며, 연결이 없어진 파일은 삭제 흐름에 넣는다. 같은 식별자에 다른 파일 아이디가 오면 거부한다.
3. 응답으로 받은 업로드 링크로 클라이언트가 파일을 올리고, 받은 백엔드 파일 아이디와 영구 주소를 본문 블록에 반영한다.
4. 클라이언트가 업로드를 마친 파일들을 업로드 완료 API로 한 번에 알린다. 서버는 파일마다 검증(업로드 기록 존재, 발급 용도, 발급자, 삭제 표시 없음, R2 객체 존재)해 업로드 완료 표시를 남기고, 일부만 성공하면 파일별 결과를 함께 돌려준다.
5. 영구 주소를 반영한 본문을 후속 임시저장·수정으로 저장하며 실패하면 재시도한다. 업로드하지 않거나 실패한 파일은 업로드 확인 예약이 정리하며 해당 영구 주소로는 파일을 제공하지 않는다. 완료 알림만 빠진 파일은 업로드 확인 예약이 R2 객체를 확인해 업로드 완료 표시를 남긴다.

### 업로드 확인 예약

- 예약 시각에 업로드 기록이 아직 미사용이고 R2에 객체가 없으면 업로드되지 않은 것으로 보고 바로 정리한다(삭제 표시 → 삭제 흐름).
- 링크 만료 직전에 시작한 업로드가 끝날 수 있도록 확인 시각은 링크 만료 시각보다 여유를 둔다. 여유 시간은 기본값을 두고, 큰 파일을 받는 경우처럼 더 필요하면 개별 API에서 따로 정한다.
- 이미 사용됐거나 R2에 객체가 있으면 아무것도 하지 않는다.
- 예약이 실행되지 않은 경우(서버 재시작 등)는 주기적 청소가 처리한다.

### 검증

업로드 기록 존재 → 발급 경로 일치 → 대상 리소스 일치 → 발급자가 요청자 → 미사용 → 삭제 표시 없음 → R2 객체 존재 순으로 확인한다. 하나라도 실패하면 제출을 거부한다.

### 삭제

1. 한 트랜잭션에서 파일을 참조하던 데이터를 정리하고 업로드 기록에 삭제 표시를 남긴다.
2. 커밋 후 R2 `DeleteObject`를 호출한다.
3. 성공(204) 또는 `NoSuchKey`이면 업로드 기록을 지운다.
4. 그 밖의 실패는 업로드 기록을 남기고 주기적 청소가 재시도한다.

### 주기적 청소

- 그때그때 정리에서 빠진 것(R2 삭제 실패, 실행되지 않은 업로드 확인 예약, 업로드했지만 제출하지 않은 파일)을 처리하는 안전망이다.
- 정해진 주기로 실행한다. 주기, 업로드 확인 여유 시간 같은 구체값은 이 문서에서 정하지 않고 정책·도메인 문서를 따른다.
- 대상은 두 가지다: 삭제 표시가 있는데 남은 업로드 기록, 그리고 업로드 확인 예약 시각이 지났는데도 사용되지 않은 업로드(연결 행으로 관리하는 첨부 파일은 연결 행이 없는 업로드).
- 미사용 업로드는 "아직 사용되지 않았고 삭제 표시가 없을 때만" 삭제 표시하는 조건부 갱신을 한 뒤 삭제 흐름 2~4를 적용한다. 그 사이 사용된 파일은 갱신되지 않아 지워지지 않는다.
- 업로드 기록마다 독립적으로 처리하고, 설정 오류(`NoSuchBucket`, 인증 실패)가 나면 전체를 멈춘다.
- 설계 상세: `sight-spring-backend/docs/plans/orphan-file-cleanup.md`

## 지켜야 할 것

- R2 객체는 DB 커밋 이후에만 지운다. 트랜잭션 안이나 커밋 전에 지우면 DB가 없는 파일을 가리킬 수 있다.
- R2 삭제 결과로 사용자 요청의 응답을 바꾸지 않는다.
- R2 호출(업로드 URL 생성 제외)을 DB 트랜잭션 안에 두지 않는다.
- `NoSuchKey`는 삭제 성공, `NoSuchBucket`은 설정 오류로 구분한다. 둘 다 HTTP 404지만 의미가 다르다.
- 업로드 기록을 조회·검증하는 곳은 삭제 표시가 없는 기록만 유효한 파일로 본다.
- 사용 중이고 삭제 표시가 없는 파일은 청소 대상이 아니다.
- 파일을 교체할 때는 새 파일 연결과 기존 파일 삭제 표시를 같은 트랜잭션에서 처리한다.

## R2 삭제 응답 참고

- S3 API의 단건 `DeleteObject`는 없는 객체를 지워도 오류 대신 성공(204)을 반환한다고 AWS가 문서화하고 있다.
- R2 문서는 없는 키를 삭제할 때의 응답을 명시하지 않는다. 구현 시 실제 응답을 확인하고, 404 `NoSuchKey`가 오더라도 성공으로 처리한다.

## 영구 주소와 레거시 이전

- 파일 접근은 소속 리소스의 영구 주소에서 권한 검사 후 Presigned GET URL로 302 리다이렉션한다. 그룹 경로는 `/groups/{groupId}/files/{fileId}`다.
- `read_url`·`read_url_expires_at`에 URL 캐시를 보관한다. 매번 권한을 검사하고 만료까지 1분 이하이면 재발급한다. 기록·임시저장 조회 응답과 본문에는 Presigned GET URL을 넣지 않는다. 그룹 파일은 그룹 열람 권한으로 제공하며 더 강한 권한의 파일은 각 기능 API에서 처리한다. 활동보고는 기존 조회 API의 임시 주소 반환을 유지한다.
- 사이트 전체 파일을 담은 `khlug_files`를 Spring에서 별도로 유지한다. 신규 업로드 테이블과 병합·선별 이전하지 않는다. `read_url`·`read_url_expires_at` 캐시 컬럼만 추가하고 분리·통합은 전체 Spring 전환 이후 결정한다.
- 기존 `/file`·`/image`는 `khlug_files`를 조회해 리다이렉션한다. 이 테이블과 객체는 신규 업로드 청소 대상이 아니다.
- 구체 계약은 [이전 계획](../../../sight-spring-backend/docs/plans/file-migration.md)과 [그룹 파일 조회](../../../sight-spring-backend/docs/plans/group/group-file-get.md)를 따른다.
