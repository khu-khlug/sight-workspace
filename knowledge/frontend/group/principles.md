# 그룹 페이지 개발 원칙

## 구조적 해결과 변경 제안

그룹 페이지는 다른 페이지보다 기능이 많고, 상태와 사용자 조작 사이의 상호작용도 복잡하다. 기능을 추가하면서 상태와 분기가 여러 곳에 흩어지면 동작을 일관되게 유지하기 어려워지므로 이 원칙을 추가한다.

기능을 구현할 때 상태와 판단 로직을 여러 곳에 흩어 놓거나, 각 사용처에 별도 분기를 추가하는 방식으로 요구사항을 맞추지 않는다. 기존 구조로 책임과 처리 흐름을 일관되게 유지하기 어렵다면 과감한 리팩터링과 구조 변경을 검토한다. 구조 변경이 필요하다고 판단한 경우에는 임의로 진행하지 않고, 변경 이유와 제안하는 구조, 영향 범위를 사용자에게 설명하여 합의한 뒤 구현한다.

## 도메인 상태의 격리와 공개 인터페이스

특정 도메인에서만 사용하는 상태와 그 상태를 변경하는 로직은 해당 도메인 안의 한곳으로 모아 격리한다. 다른 도메인과 공유가 필요하면 별도의 페이지 단위 공유 객체나 파일에 공개 인터페이스를 두고, 외부에서는 그 인터페이스를 통해 접근한다. `actions.ts`처럼 내부 구현을 감추고 필요한 조회·변경 함수와 타입을 공개하는 방식을 따른다. 공유가 필요하다는 이유만으로 내부 상태를 페이지 전역에 흩어 놓거나, 각 사용처에서 직접 변경하지 않는다.

창 상태는 창 도메인이 소유한다. 창의 콘텐츠 컴포넌트는 제공받은 인터페이스로 창을 조작하며, 창 배치나 상태전이를 직접 결정하지 않는다. `actions.ts`는 창 도메인 외부에 공개할 함수와 타입의 진입점으로 사용하고, 외부에서는 창 도메인의 내부 구현을 직접 참조하지 않는다.

`pageState.tsx`는 여러 도메인이 공유해야 하는 페이지 수명의 상태를 관리한다. 특정 도메인에서만 사용하는 상태나 영구 저장할 개인설정까지 이 파일에 모으지 않는다. 개인설정과 보관 기록처럼 이미 별도의 소유자와 공개 인터페이스가 있는 상태는 해당 진입점을 사용한다.

구체적인 파일 사용법과 기존 구조를 확장하는 방법은 [그룹 페이지 정책](policies.md)의 구현 섹션을 따른다.

## 복잡한 화면의 조작 성능

그룹 페이지는 뒤의 내용이 비치는 레이어와 복잡한 콘텐츠를 가진 창이 겹치거나 이동하는 경우가 많다. 따라서 렌더링뿐 아니라 레이아웃 계산과 화면 그리기에 드는 비용도 고려하여, 창 이동·크기 조절·스크롤·입력 중에도 조작이 부드럽게 이어지도록 구현한다.

빈번한 조작으로 발생하는 갱신은 영향을 받는 요소에 한정하고, 페이지 전체의 불필요한 재렌더링이나 반복 계산을 피한다. 매 입력이나 드래그마다 필요하지 않은 직렬화·저장·무거운 처리를 수행하지 않으며, 해당 작업이 필요한 시점에 실행한다. 반투명 효과와 애니메이션은 겹치는 영역과 함께 갱신되는 콘텐츠의 비용을 고려해 적용한다. 성능을 위해 의도한 표현이나 동작을 변경해야 한다면 변경 이유와 영향을 사용자에게 제안한다.

최적화만으로 부드러운 조작을 확보할 수 없다면 시각적 유려함을 포기하고 조작 성능을 우선한다. 예를 들어 창 이동 중에는 복잡한 콘텐츠 대신 스켈레톤을 표시하고, 이동이 끝나면 실제 콘텐츠를 다시 표시할 수 있다.
