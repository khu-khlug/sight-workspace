# 기존 일정·출석·매칭 등의 정수 ID 문자열 전환 TODO

## 작업 개요

그룹 시스템 밖에서 기존 API를 사용하는 `sight-frontend`의 일정·출석·매칭·목록 기능을 정수 ID의 10진수 문자열 계약으로 전환한다. [그룹 시스템 우선 전환](group-integer-id-frontend.md)과 분리한 후속 작업이며, [기존 정수 ID 전환 Backend TODO](existing-integer-id-migration-backend.md)와 함께 진행한다.

기존 작은 ID와 새 TSID를 정확히 구분하고, 조회·선택·변경·재시도·URL 이동에서 동일한 대상을 유지하면 완료다. 이 문서 작성으로 기존 API나 프런트 동작을 즉시 변경하지 않는다.

## 사용자와 목표

- 회원은 일정과 출석 대상, 매칭 결과를 확인하고 기존 링크로 정확한 항목에 접근한다.
- 운영진은 일정·출석·매칭을 관리할 때 선택한 대상을 정확히 조회·변경한다.
- 기존 이용자는 ID 전환 때문에 링크를 수정하거나 입력한 내용을 다시 작성할 필요가 없어야 한다.

## 사용자 경험 계약

- 일반 일정·그룹 활동 일정·빅세미나 일정의 목록·달력·상세·생성·수정·삭제에서 같은 일정 ID를 유지한다. 홈의 예정 일정과 출석 화면에서 사용하는 일정도 같은 기준을 따른다.
- 현재 출석 대상과 과거 출석 이력에서 일정 ID를 정확히 유지한다. 출석 등록과 운영진의 일정 선택·출석자 조회·추가·삭제가 선택한 일정을 대상으로 수행된다.
- 매칭 결과와 운영진 매칭 관리에서 그룹 참조를 10진수 문자열로 유지하고 해당 그룹의 조회·회원 추가·상세 이동을 정확한 대상으로 연결한다. 매칭·답변·연결 행의 기존 ULID는 유지한다.
- 그룹 상세 밖의 기존 그룹 목록·최근 그룹·일정 작성의 그룹 선택도 동일한 그룹을 가리킨다. 그룹 시스템 우선 전환에서 이미 처리한 공유 경로는 중복 변경하지 않는다.
- 기존 URL·북마크·브라우저 이력의 10진수 ID 표기를 유지한다. Base32로 재표기하거나 기존 식별자 값을 바꾸지 않는다.
- 서로 다른 큰 ID가 하나의 선택 항목이나 조회 대상으로 합쳐지지 않는다. ID의 크기·문자열 순서로 날짜 정렬·목록 순서를 대신하지 않는다.
- 기존 출석·매칭·일정의 권한과 상태별 행동, 페이지네이션·검색·정렬 방식은 유지한다.

## 허용 및 제한 정책

정책 변경 없음

## 입력 및 복구

- 전환 대상 ID는 선행 0 없는 양의 Long 범위 10진수 문자열로 검증한다. 안전 정수 상한을 넘는다는 이유로 유효한 ID를 거부하지 않는다.
- 일정 선택과 그룹 선택, URL 해석, API 요청·응답에서 대상 ID를 숫자로 변환하지 않는다. 숫자 JSON을 받은 뒤 문자열로 바꾸는 방식으로 정밀도를 복구하려 하지 않는다.
- 조회·저장 실패 시 선택한 일정·그룹과 작성한 입력을 유지한다. 재시도에서도 같은 문자열 ID를 사용하며 다른 대상에 요청하지 않는다.
- 전환 대상 ID가 브라우저에 저장되는 기존 경로는 함께 변경한다. 기존의 안전한 양의 정수 숫자는 정확한 문자열로 옮기고, 정밀도가 보장되지 않는 값으로 자동 변경 요청을 보내지 않는다. 복구할 수 없는 대상은 안내하고 작성 내용은 임의로 지우지 않는다.
- 날짜·연도·월·학기·수량·회원 번호 등의 기존 숫자 입력과 출석 인증 코드 표현은 유지한다.

## 데이터 및 연동

source of truth는 Backend다. 대상 필드와 API 계약은 [기존 정수 ID 전환 Backend TODO](existing-integer-id-migration-backend.md#http-api-계약), 발급·전송 원칙은 [TSID 결정문서](../../sight-spring-backend/docs/decisions/integer-id-tsid.md)를 따른다. JSON 문자열은 JavaScript 정밀도를 보존하며, 10진수 표기는 레거시 식별자와 URL 호환성을 유지한다.

| 소비 기능 | 문자열로 전환할 대상 |
| :-- | :-- |
| 일정 조회·생성·수정·삭제 및 홈 예정 일정 | 일정 ID와 포함된 그룹 참조 |
| 그룹 활동 일정 작성 | 선택 그룹과 요청의 그룹 ID |
| 현재 출석·출석 이력·출석 등록 | 참조하는 일정 ID |
| 운영진 출석 관리 | 선택 일정 ID와 출석자 조회·추가·삭제 요청의 일정 ID |
| 회원 매칭 결과·운영진 매칭 관리 | 매칭 대상 그룹 ID와 결과에 중첩된 그룹 참조 |
| 기존 그룹 목록·최근 그룹·그룹 선택 | 목록 항목과 선택 결과의 그룹 ID |

- API 타입·응답 변환·요청 인자·선택 상태·주소·기존 저장 데이터·해당 개발 목업의 대상 ID 표현을 함께 맞춘다.
- 회원 ID·학번·수량·경험치·페이지 번호와 기존 ULID 문자열은 전환 대상이 아니다. 출석자 삭제 요청에서도 회원 ID는 기존 계약을 유지한다.
- Backend는 해당 API의 문자열 계약과 채번 변경을 함께 준비하고 Frontend 제공 시점을 맞춘다. 숫자 응답을 사용하는 구 소비자가 TSID를 받는 상태로 채번부터 활성화하지 않는다.
- 그룹 시스템과 데이터를 공유해 새 TSID를 읽을 수 있는 경로는 후속 작업까지 미룰 수 없다. [그룹 전환 Task](group-integer-id-frontend.md)에서 소비자까지 함께 처리하거나 Backend의 해당 TSID 쓰기를 보류한다. 나머지 경로만 이 후속 Task에서 전환한다.
- 내부 그룹 채널 API의 별도 소비자 전환은 Backend TODO가 추적한다. 해당 소비자가 `sight-frontend`가 아니라면 이 프런트 Task의 구현 범위에 포함하지 않는다.

## 사용자 보호 및 개인정보

ID 정밀도 손실로 다른 일정·그룹에 출석 등록·수정·삭제를 요청하지 않게 한다. 기존 인증·인가와 확인 절차를 유지한다. URL에 출석자 명단·작성 내용 등의 개인정보를 추가하지 않는다.

## 검증

동작 확인은 사용자가 수행한다. 에이전트는 명시적 요청 없이 테스트·타입 검사·브라우저 조작을 실행하지 않는다.

- 기존 작은 ID와 큰 TSID로 일정 목록·달력·홈 예정 일정·상세를 열고 생성·수정·삭제가 정확한 대상에 적용되는지 확인한다.
- `9007199254740992`와 `9007199254740993` 같은 서로 다른 큰 ID가 선택 목록·조회 결과·요청에서 구분되는지 확인한다.
- 출석 링크·현재 출석·이력과 운영진 출석자 조회·추가·삭제가 같은 일정을 참조하는지 확인한다. 출석자 회원 ID와 인증 코드는 기존 표현을 유지해야 한다.
- 그룹 활동 일정의 선택 그룹과 매칭 결과·운영진 회원 추가·그룹 목록의 상세 이동이 원래 그룹을 가리키는지 확인한다.
- 기존 링크·새로고침·뒤로가기와 실패 후 재시도에서 ID·선택·입력을 유지하고, 유효하지 않은 ID로 다른 대상에 변경 요청을 보내지 않는지 확인한다.
- API·개발 목업·주소·저장 데이터의 정밀도 보존을 정적으로 대조하고, 대상 이외의 숫자와 ULID가 유지되는지 확인한다.

## 비목표

그룹 상세의 카드·리스트·기록·로그 전환은 별도 그룹 Task에서 수행한다. Backend 채번기 구현, 기존 데이터 재채번, 회원 ID의 TSID 전환, 전체 숫자의 문자열화, 세미나 관리 구조 개편은 이 Task에 포함하지 않는다.
